# Anonymous demo — design and delivery plan

- Date: 2026-10-21
- Status: Recommendation for future implementation; this PR changes documentation only.
- Source baseline: `origin/dev`, commit `54286e869130b8a352c8858738b2a5cb694303f5`, fetched and inspected on 2026-10-21.

## Decision

Add a public `/demo` page containing an interactive sample workspace. Use authored fictional data and a dedicated React state provider held entirely in browser memory. Chat replies are explicitly scripted. Do not create a guest account or server workspace, call inference, or connect the demo to production data services.

This demonstrates the builder, preview, and conversation workflow without requiring login, spending inference budget, or introducing guest authorization and cleanup infrastructure. It cannot demonstrate live model quality; the UI must say so before the visitor sends a message. An account remains the path to configuring and running a real agent.

## Visitor experience and feature boundary

Visitors enter through a new **Try demo** link on the landing page or sign-in page, or by opening `/demo` directly. Keep existing sign-in, sign-up, and post-login destinations. The demo uses in-page navigation for agent selection, setup, knowledge, preview, and conversations; it does not navigate into protected `/agents` pages.

Show **Sample workspace**, **Scripted responses — no live AI**, and **Changes are temporary and disappear when you leave or reload** prominently. Provide **Reset demo**, an exit to the landing page, and an optional **Create an account** link to `/sign-up`. Do not automatically migrate demo messages or edits into an account. A signed-in visitor can open the same sample workspace without switching their active tenant.

| Area          | Included in the first demo                                                                                                      | Limits                                                                                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent list    | Two fictional agents: an information provider for a fictional visitor centre and a feedback collector for a fictional event     | No creation, deletion, publishing, or sharing of real agents                                                                                                                          |
| Setup         | Inspect sample setup; edit the selected agent's name and greeting locally                                                       | Name updates the workspace and preview; greeting appears in a new preview conversation. Instructions remain read-only because scripted replies do not evaluate arbitrary instructions |
| Knowledge     | Inspect authored sample source text used by the information-provider script                                                     | No uploads, ingestion, embeddings, external fetching, or editing knowledge sources                                                                                                    |
| Preview chat  | Suggested questions and a guided feedback sequence with deterministic replies                                                   | A visible fallback for other text: “This demo uses scripted replies. Try a suggested question or create an account to use live AI.” No inference or arbitrary instruction execution   |
| Conversations | Inspect fictional sample transcripts and conversations generated locally during this visit, including collected sample feedback | No account history, production records, exports, or persistent storage                                                                                                                |

Also exclude provider credentials, integrations, webhooks, scheduling actions, notifications, billing, and account management. Omit controls for unavailable actions or label them unavailable without attaching production handlers. Use fictional feedback rather than soliciting personal information. Both agents should have complete guided paths, not dead-end controls.

## Data isolation and proposed component boundary

Fixtures are authored for this demo, never copied from customer records. Use `demo-` prefixed IDs for agents, conversations, and messages. IDs help identify fixtures; isolation comes from the absence of a production data path, not from the prefix.

Mount the dedicated provider only within `/demo`. Reuse presentation primitives such as buttons, cards, tabs, and message rendering after checking their imports and effects. Do not reuse production server actions, tenant-context helpers, data clients, or chat components that call APIs. No demo operation may create users, tenants, database rows, inference requests, auth/access/external-session cookies, or change `active_tenant_id`.

Proposed future interfaces (these files are not added by this PR):

| File under `apps/web/`               | Responsibility                                                                                           |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `app/demo/page.tsx`                  | Public page outside the protected agents layout; mounts the demo workspace                               |
| `components/demo/demo-workspace.tsx` | Demo navigation, disclosures, setup, preview, and conversation inspection                                |
| `components/demo/demo-provider.tsx`  | Owns local state and visit lifecycle; no account context                                                 |
| `lib/demo/types.ts`                  | Demo-only `DemoState` and `DemoAction` types                                                             |
| `lib/demo/fixtures.ts`               | Fictional agents, source text, transcripts, and scripted response definitions                            |
| `lib/demo/state.ts`                  | `createInitialDemoState(): DemoState` and `demoReducer(state: DemoState, action: DemoAction): DemoState` |

State contains `selectedAgentId`, `agents`, `conversations`, and `activeConversationId`. Actions select an agent, update its name/greeting, submit a message, start a conversation, and reset. Starting a conversation uses the current local greeting; existing transcripts retain their messages. Script selection and feedback collection operate on local state. Reset creates fresh copies of all fixtures, including default selection and active conversation; never mutate shared fixture objects.

There is no proposed `/api/demo` endpoint, schema migration, server session, guest token, or dependency change. Do not send message contents or edits to analytics or other external services. Normal page delivery, static assets, and existing root-layout session checks remain baseline infrastructure; demo interactions themselves must not use account context or production services. In particular, the existing root layout can resolve theme for a signed-in user; this proposal does not claim that rendering the entire application shell performs zero server reads.

## Reset and lifecycle

Default to a fresh visit, with no saved demo activity between visits. Keep edits and conversations only in provider memory during the current visit; do not use localStorage, sessionStorage, IndexedDB, cookies, URL state, or server persistence for activity.

- **Reset demo** immediately replaces all state with fresh fixtures, including local edits, messages, feedback, and selection.
- Reload, leaving `/demo` and returning, opening a new tab, and browser-history restoration each start fresh. Switching between in-page demo views retains current-visit state.
- A provider remount alone is insufficient for browsers that restore a page from the back/forward cache. Future implementation must explicitly handle page restoration (for example, a `pageshow` handler for persisted restores) and cached client navigation, with browser coverage proving fresh entry. Place the provider at the page boundary rather than a persistent shared layout.
- An idle visitor can keep the current in-memory visit open; there is no time-based expiry promise. Leaving, reloading, or resetting discards it. No server expiry, scheduled cleanup, or shared sandbox exists.

## Alternatives and trade-offs

| Approach                                      | Benefits                                                                                                                                          | Costs and reason for decision                                                                                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser-memory sample workspace — recommended | Immediate anonymous entry; predictable interactions; no guest authorization, production-data access, inference expense, or cleanup infrastructure | Scripted chat cannot prove live model quality; fixture and presentation parity require maintenance. Disclosures and limited edits keep expectations accurate                                              |
| Existing anonymous public agent               | Smaller route/UI change; demonstrates real model responses                                                                                        | Demonstrates chat rather than the builder; persists real activity and invokes inference with existing usage, access, and rate-limit concerns. Keep as an existing product feature, not the workspace demo |
| Per-visitor server sandbox                    | Higher fidelity, potentially real editing and live AI                                                                                             | Requires scoped guest authorization, quotas, persistence rules, expiry, cleanup, abuse controls, and budget decisions. Revisit only if validated demo needs exceed the sample workflow                    |

## Assumptions and remaining product decisions

The first version includes the two agents and feature limits above and starts fresh each visit. These are recommended defaults that resolve the feature and persistence questions for this plan. Expanding to arbitrary instructions, live inference, uploads, or saved activity would require a new design review of the data and authorization boundary.

Use the existing Next.js application and Cloud Run hosting/release process; assume no separate service or hosting capacity. No deadline or additional hosting constraint was supplied, so this plan promises no delivery date. Confirm capacity and timing during future implementation planning. The fixture owner should review the sample flows when corresponding product screens change.
